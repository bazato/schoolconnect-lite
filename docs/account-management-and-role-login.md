# Account management and role-based login

## Behavior

- A phone number identifies one Identity user, with independent memberships for each school and role. Parent, Teacher and School Administrator must each be explicitly registered by an authorized administrator; selecting a role at login never grants it.
- The mobile login asks which registered role to use. The web portal supports School Administrator and Platform Owner. A signed server session selects the role; the UI is not the authorization boundary.
- The existing four-digit passcode is shared across this phone's memberships. After first-time invitation/OTP activation, adding another role to an already activated phone does not require another passcode or duplicate invitation. Mock OTP remains `123456` in the configured trial environment.
- Repeating or concurrently retrying account provisioning reuses the membership and pending invitation, rather than issuing duplicate registrations. Parent registration for another child links the additional child to the same parent membership.
- New school, class and student identifiers are generated by School. Subject identifiers are derived from the subject name. Existing/imported identifiers remain supported; manual creation does not require entering technical codes. Grade is selected from predefined values in the web form.

## Management permissions

- Platform owners manage schools, platform owners, school administrators, and the selected school's classes, teachers, students and parents. Owner-selected school scope is authorized centrally, then bound to the request; a client-supplied body school ID cannot change it.
- School administrators manage their own school's classes, teachers, assignments, students and parents. They can edit school administrator names/phones and view/reissue activation codes, but cannot grant themselves owner access or remove fellow administrators. Platform owners manage administrator access.
- “School owner” uses the existing School Administrator role, not a newly invented role.
- Delete closes a school, archives a class, inactivates a student, or revokes a role. Historical results, attendance, fees and audit records are retained. The last active platform owner cannot be revoked, including through concurrent requests.
- Teacher assignments are keyed to membership, so a teacher can retain multiple class assignments when their phone is corrected.

## Phone correction

Changing a phone affects only the selected membership. It does not rewrite the old phone's unrelated memberships or credentials. Sessions currently using the changed membership are revoked.

If the target phone already exists, it keeps its own passcode. If the target phone is new, it receives an activation invitation and must verify OTP and set a passcode. The editor displays the newly generated code before refreshing, important when an administrator corrects their own phone.

If the target already has the same school/role membership, editing returns a conflict rather than silently merging historical accounts. Registering the role normally reuses that existing membership.

Parent phone changes capture the authorized child IDs at the gateway. The Identity transaction commits the membership change and its outbox event together. The existing outbox publisher sends to Kafka; an embedded School consumer applies the child-link transfer with an event inbox for idempotency. There is no new standalone worker and the existing two-second publisher polling is unchanged.

School resolves current Identity ownership when consuming, so delayed/replayed events cannot restore stale account ownership. Only captured children move; children subsequently linked to the old identity do not. School-scoped child aliases preserve access to historical private results/timelines. Authorization still requires a current guardian-child relationship first. Historical notifications/audit records are not rewritten to another identity. Child visibility can take a few seconds while the event propagates; failures use the existing quarantine/replay mechanism.

## Activation-code storage

New codes retain a verification hash and additionally store AES-256-GCM ciphertext for authorized redisplay. The invitation ID is authenticated associated data. Codes are not added to events or tokens.

`INVITATION_CODE_KEY` accepts a private secret of at least 32 bytes. If absent, the existing `AUTH_JWT_SECRET` is used with domain separation. Keep the key stable and backed up; changing it without a migration makes old displayed codes unavailable, though their hashes remain verifiable. Legacy hash-only codes cannot be recovered: explicitly reissue once if redisplay is required. Active accounts may have no activation code because they already use a passcode.

## Migration and rollout

1. Back up databases and follow the normal managed migration process. Migration `105-account-management.sql` adds Identity ciphertext/indexes and School's membership-event inbox, guardian aliases and consumer-failure storage. It is included in the managed migration manifest and does not seed users.
2. Apply the migration before starting the updated Identity and School services. Deploy Authorization, gateway, Content and Read changes together to support selected owner scope and guardian aliases. Custom `AUTHORIZATION_ROUTE_RULES_JSON` configurations must explicitly include the new DELETE routes and owner `selectableSchoolRoles` where desired; custom rules are not silently expanded.
3. Verify Kafka connectivity, School consumer health and quarantine counts. Keep Identity/School internal services inaccessible to public clients.
4. Deploy the web portal and issue a new Android build for mobile role selection and generated-code creation forms. Previously published APK 0.1.5 does not contain this feature.

No production migration, deployment, Git push or new Android build was performed as part of this local implementation.

## Verification

`pnpm test:accounts` now runs the original 13 account acceptance scenarios and three school-announcement scenarios against five disposable localhost PostgreSQL databases and a dedicated real Kafka topic. It verifies generated identifiers, encrypted redisplay, same-phone roles, role-specific login/activation, concurrent provisioning, phone correction, child-history access/isolation, idempotent consumption, role-only revocation, last-owner concurrency protection and recoverable school closure. It removes only its own test databases/topic. It explicitly publishes transactional outbox rows to test the transport/consumer; it is not a production outbox-throughput or physical-device test. Announcement changes and their verification are documented in `school-wide-announcements.md`.

Verification completed locally: 308 unit/API/component tests passed across the eight affected services/clients, 15 managed-runtime/migration tests passed, and all 13 disposable PostgreSQL/Kafka acceptance scenarios passed. Lint, type checks, six backend builds, the web production build and Expo web bundle export passed. Fourteen existing opt-in Identity/Read database tests remained skipped; the disposable acceptance test supplies real database coverage for this change.

Native installation, live deployment, browser/device acceptance and production load testing remain release checks. File scanning/upload availability and the mocked/live OTP boundary are unchanged. The Neon skill guidance was applied by retaining the existing custom Identity system and testing schema changes in isolated local databases rather than migrating authentication providers or changing the live Neon database.
