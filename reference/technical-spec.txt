SchoolConnect Lite
FINAL DEVELOPMENT TECHNICAL SPECIFICATION
Single mobile application | Teacher + Parent | School communication and attendance
Version 1.0  •  07 September 2026  •  Implementation baseline
Executive technical decision
Build one React Native mobile app with Expo and TypeScript, a Node.js/NestJS modular backend, PostgreSQL, private S3-compatible object storage and asynchronous notification/file workers. Use a small restricted administration console for school onboarding and support. Start with independently scalable API and worker deployments, not a full microservice estate. Extract domain services only when measured scaling, isolation or team ownership justifies it.
This document turns the approved business baseline into concrete implementation decisions. Values marked “proposed” are engineering defaults requiring confirmation during discovery; they are not claims that the school has already approved them.

1. Scope and traceability
The approved business specification defines one role-aware application, four daily jobs, eight mobile wireframes and a 10–12 week indicative MVP. This technical baseline preserves that scope. The larger HLD contributes tenant isolation, authoritative records, private attachments, auditable corrections and independently scalable workers; its fees, AI and ERP expansion are not imported into this release.
1.1 Included and excluded
Included: authentication, role switching, school/class/subject setup, guardian links, teacher assignments, three post types, secure attachments, parent timeline, attendance entry/correction, acknowledgement/leave note, push/in-app inbox, delivery/view reporting, audit and pilot support.
Excluded: fee collection, transport, chat, AI tutor, automated mark calculation, report-card generation, student social accounts, payment integration and unrestricted school-wide file sharing.
An operational admin console is necessary for roster import, account activation, assignment management, result-publishing permissions and correction review. It is not a second mobile application or a full ERP.
2. Decisions and assumptions
Open decisions must be recorded in an ADR register with owner, decision date, alternatives and impact. Do not silently substitute a different product rule during development.
3. Technology and architecture
Use a supported Node.js LTS release and compatible maintained NestJS, Prisma and Expo versions. Pin exact versions and lockfiles during repository initialization; verify current support and security patches before deployment. Do not upgrade major versions during pilot hardening.

4. Identity and authorization
4.1 Authentication and session design
School administrator imports or creates a staff/guardian account, links it to the correct school and issues an invitation. Phone verification is completed through a rate-limited OTP provider adapter. The NestJS authentication module owns identity verification and session lifecycle; domain modules own school membership, teacher assignments and guardian relationships. Store only hashed OTP challenges and hashed refresh credentials. Do not store plaintext passwords, OTPs or tokens.
Use a native OTP login flow over HTTPS. The backend verifies the challenge and issues a short-lived access token plus an opaque rotating refresh token. If an external identity provider is introduced later, use Authorization Code with PKCE and the system browser.
Access token proposed lifetime 5–15 minutes. Use opaque, cryptographically random refresh tokens stored only as keyed hashes server-side, rotated atomically on use. Enforce idle and absolute session expiry, refresh-token reuse detection, revocation and device-level logout. Never issue perpetual refresh credentials.
Store refresh credentials in OS-backed secure storage. Clear local sensitive cache on logout, account revocation or role/school switch.
API validates issuer, audience, signature, expiry and token type. Never trust a client-supplied role, school ID or student ID as proof of authorization.
OTP: proposed 6 digits, 5-minute validity, maximum 5 attempts, resend cooldown and per-phone/IP rate limits. Store only keyed hashes of challenges if managed internally; do not log codes.
Staff MFA is required for school administrators and result-publishing approvers; rollout to teachers can be configured by school policy.
4.2 Context and policy evaluation
Authenticated principal
  -> active school membership
  -> active role permission
  -> resource school/ownership
  -> teacher assignment OR guardian-child link
  -> audience / publication / consent checks
  -> allow or deny (default deny)
A user may hold both Teacher and Parent roles. Role switching changes navigation and active context, not identity. Each request carries an active membership identifier; the server resolves the membership and rejects inactive or mismatched context. A teacher’s parent role never grants access to other students.
4.3 Tenant isolation
Every tenant-owned table contains school_id. Foreign keys and unique constraints must prevent cross-school references. Repository queries require explicit school scope; PostgreSQL RLS is recommended as defense in depth with transaction-local tenant context and a non-bypass application role. Background jobs establish tenant context explicitly. Integration tests must attempt cross-school access with valid IDs and valid tokens.
Guardian relationship revocation takes effect on the next request, including existing signed-download issuance. Use short-lived download URLs and revoke cached sensitive data on the next authenticated sync. Never authorize a result solely because the parent belongs to the same class.
5. Data model and migrations
Use UUID primary keys, timestamptz in UTC, optimistic version columns for mutable aggregates and explicit foreign keys. Store school-local dates separately from timestamps. All unique constraints involving tenant-owned entities include school_id where appropriate. Avoid generic JSON blobs for authoritative attendance, relationships or permissions.

5.2 Critical relational rules
Use composite foreign keys (school_id, referenced_id) where tenant-owned relationships cross tables. Add corresponding unique keys to referenced tables. Reject cross-tenant references at the database boundary.
Posts and post revisions are separate. A published revision is immutable; corrections create a new revision and atomically update current_revision_id.
Result attachments are associated with a student-private recipient or explicitly approved class-public classification. A single result file must never be inferred to be private merely because its post has a class audience.
Attendance_current points to the authoritative latest event. Historical attendance_events are append-only. Parent responses reference the original event and remain intact after correction.
Store notification recipient snapshots so publication reporting is reproducible. Re-check live guardian authorization when content is opened; a snapshot is not an access grant.
Do not put binary files, access tokens, OTPs, raw push tokens or full student documents in audit/outbox payloads.
5.3 Migration strategy
Prisma Migrate migrations are immutable after release. Use expand–migrate–contract for schema changes, including nullable additions, backfill, application compatibility and later constraint enforcement. CI runs migrations against a clean database and a copy of the previous schema. Production migrations require backup verification, review and a rollback plan; destructive migrations are not automatically reversed.

6. Publishing and attachment workflows
6.1 Post lifecycle
DRAFT -> UPLOADING -> READY -> PUBLISHED -> UPDATED -> ARCHIVED
             |           |         |
             +-> FAILED -+         +-> correction creates revision
DRAFT -> DELETED (soft delete, retention policy)
PUBLISHED/UPDATED -> ARCHIVED (audit retained)
READY is an internal validation state; the user sees Draft, Uploading, Published, Updated or Archived. A post with no required attachment may become READY immediately. Publication is a transaction that validates current permissions, file readiness and audience, creates recipient snapshots, updates status and writes an outbox event.
6.2 Homework rules
Required: assigned section, subject, title (1–150 characters), instructions (1–5,000 characters), due date. Attachment optional unless the school config requires one.
Due date uses school-local calendar date; optional due time is stored with timezone. Reject due dates before publication date unless an authorized historical-post override is supplied.
Teacher may create drafts and publish only to active assigned sections/subjects. Multi-section publishing requires an explicit assignment for every selected section.
Parent sees homework only through an eligible linked student. No student submission, grading or completion tracking is included in MVP.
Material corrections create a new revision, Updated label and new notification. Minor metadata corrections may suppress push but remain audited.
6.3 Results and privacy
The business baseline allows result attachments to class/child audiences. The implementation resolves this ambiguity conservatively: student-specific marks and report cards must be distributed as individual private files. A class-wide result attachment is permitted only if school policy explicitly classifies it as safe for all recipients and an authorized publisher confirms that classification. The system must not automatically inspect a PDF and assume it is safe.
Required: exam name, subject, audience, attachment and privacy classification. A private result requires explicit student_id association for each file.
For batch upload, the admin/teacher maps each file to an admission number using a validated manifest. Show a preview of student name, admission number and filename before publication.
Reject duplicate or unmatched admission numbers, missing files, unsupported types and files whose scan is incomplete. Do not publish partial batches by default.
Require an explicit privacy confirmation and a second authorized approval if the school enables two-person result release. The author cannot approve their own batch when separation of duties is enabled.
Result push text is generic. Never include marks, grades, student names or document URLs in push payloads. Access is reauthorized on every file-open request.
Corrections retain prior versions and access history. A replaced result is not accessible through normal parent navigation; authorized audit retrieval remains possible.
6.4 Announcements
Required title and message; optional attachment. Audience is section, grade or school. School-wide publishing requires a separate permission. Urgent classification is limited to authorized staff and is audited. Save draft, preview audience count and publish now are MVP actions. Scheduled publishing and quiet-hour controls are deferred unless the pilot school explicitly requires them.
6.5 Attachment pipeline
1. Client requests upload session with name/type/size/checksum.
2. API validates actor, owner, quota and allowed type; returns short-lived upload URL.
3. Client uploads directly to private quarantine storage.
4. Client completes session; server HEAD-checks object size and checksum.
5. Worker validates magic bytes, scans malware and checks file structure.
6. Clean object is copied/moved to private clean storage; metadata becomes READY.
7. API allows publication only when every required file is READY.
8. Parent requests file access; API rechecks live relationship and audience.
9. API returns short-lived signed URL or authenticated streaming response.
10. Access attempt and outcome are recorded without logging document contents.
Signed URLs are bearer capabilities and cannot be reliably revoked after issuance. Keep them short-lived, never place them in notifications or logs, and use authenticated streaming where immediate revocation is required. File scanning is not a guarantee that a document is harmless; maintain defense-in-depth and incident procedures.
6.6 Publish transaction pseudocode
publish(postId, expectedVersion, idempotencyKey):
  authenticate(); resolveActiveMembership()
  begin transaction
  lock post; assert version and DRAFT/READY state
  authorize publisher for every requested audience
  validate revision and all attachment scan states == READY
  resolve eligible students and active guardian recipients
  validate result privacy classification and file mappings
  persist immutable revision + recipient snapshot
  set PUBLISHED, publishedAt, increment version
  insert audit event + PostPublished outbox event
  commit
  return postId, version, publishedAt, recipientCount
Do not call the push provider inside the database transaction. Outbox workers are at-least-once; recipient/event deduplication must make repeated processing safe. Recipient count is a snapshot, not proof of delivery.
7. Attendance and acknowledgement
7.1 Official attendance model
Attendance is recorded per student and school-local date. MVP statuses are PRESENT, ABSENT, LATE and LEAVE; schools must approve whether LATE/LEAVE count as present for reporting. The authoritative current row points to an immutable event revision. A teacher may enter or correct attendance only for an assigned class and permitted date window.
7.2 Attendance submission
Teacher opens assigned roster -> selects date -> marks students
 -> submits with expected roster/date version and idempotency key
 -> server validates enrollment, assignment and date window
 -> transaction writes event revisions + current pointers + audit
 -> absence transitions create notification outbox events
 -> worker creates guardian inbox items and attempts push
A class submission must be atomic by default: invalid students or stale versions reject the batch with row-level errors. No silent partial attendance. Duplicate requests return the original result. Repeated submission of unchanged status does not create duplicate absence alerts.
7.3 Parent acknowledgement
ABSENT event -> response PENDING
  -> guardian opens alert -> explicit Acknowledge
  -> ACKNOWLEDGED (actor + timestamp)
  -> optional reason / leave request -> SUBMITTED
  -> school review -> APPROVED or REJECTED
Attendance correction -> new official event; historical response retained
Acknowledgement means the guardian confirms seeing the absence alert. It is not a claim that the absence is justified and is not attendance approval.
The first explicit acknowledgement per guardian/event is idempotent. Additional reason updates create append-only response revisions or a new leave-note event, not an overwrite of historical evidence.
If two guardians are linked, each has an independent response. School-level follow-up can be configured as “any guardian acknowledged” or “all guardians acknowledged”; default is any guardian, with individual evidence retained.
If the attendance event is corrected to PRESENT, mark the pending alert superseded and cancel unsent reminders. Preserve prior acknowledgement and show “Attendance corrected” in the history.
Leave approval is a separate staff action and does not automatically change official attendance. Any attendance correction requires an authorized actor, reason and new event revision.
No acknowledgement is inferred from push delivery, notification opening, content view, timeout or another guardian’s action.

9.6 Mobile implementation details
Use generated API types and a centralized HTTP client with token refresh single-flight, timeout, correlation ID and normalized errors.

10. Notifications and offline behavior
10.1 Notification event model
The in-app notification row is authoritative. Push is best-effort transport. Distinguish QUEUED, PROVIDER_ACCEPTED, PROVIDER_REJECTED and UNKNOWN; do not label provider acceptance as device delivery. “Viewed” is recorded only when the content screen is opened and the server accepts the view event. “Acknowledged” requires the explicit action.
10.2 Worker delivery algorithm
claim pending outbox rows using FOR UPDATE SKIP LOCKED
 -> deserialize versioned event
 -> resolve/create recipient notification with unique event+recipient key
 -> send push with provider-specific idempotency/deduplication
 -> record attempt and provider response
 -> mark event processed or schedule exponential retry
 -> dead-letter after configured attempts; alert operations
Proposed retries: 1, 5, 15, 60 minutes with jitter, then dead-letter review. Permanent invalid-token errors disable the device token. Never retry malformed payloads indefinitely. A scheduled reconciliation job finds stale pending events and orphaned delivery attempts.
10.3 Offline policy
Offline queues are encrypted where feasible, bounded by size and age, and tied to the authenticated account. Never silently overwrite server changes. Show conflicts and require user resolution. A queued acknowledgement of a superseded event is rejected and replaced by the current status display, not silently applied to another event.
11. Security and privacy
11.1 Threat model and controls
11.2 Data classification
Use TLS 1.2+ with modern cipher configuration, encryption at rest, managed secrets and least-privilege service identities. Do not embed backend secrets, storage credentials or privileged API keys in the mobile bundle. Restrict production database and storage access to approved operators; all support access must be logged.
11.3 Privacy and legal readiness
Before pilot, obtain school-approved privacy notice, data processing agreement, guardian-link verification procedure, retention schedule, incident contact and deletion/export process. Assess applicable Indian data-protection and child-data requirements with qualified counsel; do not assume a particular consent or retention rule is automatically satisfied by technical controls. Confirm hosting location, subprocessors and cross-border transfers.
11.4 Audit event contract
AuditEvent {
 id, schoolId, actorId, actorRole, action,

}
Audit records are append-only to application users. Record publish/edit/archive, result access, attendance changes, acknowledgement, leave review, permission changes, imports and support access. Do not store full document contents or sensitive free-text reasons in generic audit metadata. Use separate restricted evidence storage where necessary.
11.5 Retention and deletion
Retention defaults in Section 2 are proposals only. Implement per-data-class retention policies, legal holds, export and deletion workflows. Revoking a guardian link removes access but does not automatically delete official school records. Account deletion must distinguish identity removal, school record retention and legally required audit evidence. Backups have separate expiry and documented restoration/deletion limitations.

15.1 Domain events

15.2 Idempotency implementation

16. Architecture revision: Node.js and scaling
Version 1.1 amendment • Supersedes the Java-specific implementation choices in version 1.0. All functional requirements, privacy rules, data contracts and acceptance criteria remain unchanged. The selected backend is Node.js with NestJS and TypeScript. Java/Spring Boot remains a valid alternative if team expertise or future workload requirements justify it.
16.1 Final technology decision
16.2 Scaling is not the same as microservices
A modular monolith can scale horizontally. Multiple stateless API instances can serve the same application behind a load balancer, while notification and file workers scale independently. Microservices become useful when a domain needs independent deployment, isolation, ownership or materially different scaling. They are not required merely because the number of schools or users increases.

      |

      |

      |

      +-- Notification workers: 1..N
      +-- File processing workers: 1..N
Scale API replicas based on CPU, memory, latency and request concurrency; scale workers based on queue age, processing time and failure rate. Database connection capacity, query efficiency, indexes, storage bandwidth and external-provider limits must be measured independently. Adding API replicas does not automatically solve a database bottleneck.

Each module owns its controllers, application services, domain policies, persistence adapters and public interfaces. Other modules must not import internal repositories or entities. Shared packages contain stable contracts and utilities, not a shared mutable domain model. Use dependency rules and architecture tests to prevent accidental coupling.
16.4 Service extraction criteria
Extraction requires an ADR, owned data model, API/event contracts, migration plan, service authentication, observability, retry/idempotency design and rollback strategy. Do not split services merely to create one service per database table or business screen.
16.5 Node.js runtime and CPU workload rules
Node.js is well suited to I/O-heavy APIs, database access, notifications and service orchestration. CPU-heavy synchronous JavaScript can block the event loop and delay unrelated requests. PDF conversion, OCR, large image processing and expensive computation must run in bounded workers, worker threads or specialized external processes. Native libraries may use their own thread pools, but their concurrency and memory consumption still require limits.
Do not perform malware scanning or expensive document processing inside an HTTP request. The API accepts uploads, records state and returns promptly; workers process files asynchronously. Use timeouts, bounded queues, memory limits and backpressure. A separate Java, Go or Python processor is acceptable later without changing the core Node.js architecture.
16.6 Transactions, outbox and distributed consistency
await prisma.$transaction(async (tx) => {
  // Lock/validate aggregate version and authorization.
  // Persist post revision and recipient snapshot.
  // Persist audit event and outbox event.
  // Commit together; never send push inside transaction.
});
The example is conceptual: implement optimistic concurrency or explicit row locking as required by the database operation. Prisma transaction APIs and raw SQL must be used with verified supported semantics. External storage and push operations are not part of the database transaction. Use upload readiness checks, transactional outbox, idempotency keys and compensating actions where necessary.
If domains are extracted, each service owns its data and commits locally. Cross-service workflows use versioned events, retries, idempotent consumers and explicit eventual-consistency states. A saga is appropriate only where a genuine multi-service business transaction requires compensation; do not introduce a distributed transaction framework for the MVP.

16.8 Production deployment and cost
Node.js and Java both support production-grade horizontal scaling and microservices. Node.js may use less memory for some small API workloads, but actual cost depends on framework, dependencies, traffic, database pools, worker concurrency and hosting. No fixed percentage saving is guaranteed. Java should not be rejected solely to reduce hosting cost.

Replace Java-specific build steps with Node.js/TypeScript compilation, linting, Jest unit tests, Supertest API tests, Prisma migration validation and Testcontainers integration tests. Keep all original functional and security tests. Add event-loop delay, heap usage, worker backlog, database pool saturation and graceful-shutdown tests.
Release gates: no blocking CPU work in API handlers; all critical writes are transactional/idempotent; worker retries do not duplicate logical notifications; multiple API replicas pass concurrent publish/attendance tests; revoked guardian access is denied across replicas; worker failure does not lose committed business events; production secrets are mandatory and never defaulted.
16.10 Final architecture decision record
ADR-001 revision: Adopt Node.js/NestJS/TypeScript for the backend because it supports the MVP’s I/O-oriented workloads, shared TypeScript expertise and future service extraction. Microservices are an optional evolution based on measured needs, not a prerequisite for scaling. Java/Spring Boot remains an acceptable alternative; changing runtime does not change product scope or security obligations.

17. Authentication revision: lightweight NestJS identity
Version 1.2 amendment • Supersedes the Keycloak-specific requirements in earlier sections. The MVP will use application-managed authentication inside NestJS. Keycloak is not required for production deployment. All existing school, teacher, guardian, student and result authorization rules remain mandatory.
17.1 Decision and scope
Use a private, invitation-only, phone-OTP authentication flow for the initial pilot. Do not implement password login, social login or public registration unless explicitly approved. A dedicated identity provider may be introduced later for enterprise SSO, federation or centralized identity policies. Removing Keycloak reduces a separate runtime and operational dependency but transfers responsibility for session security, abuse prevention and identity lifecycle to the application team.
17.2 Identity architecture

The authentication module is not a separate microservice initially. Its public interfaces must be isolated so an external OIDC provider can replace token issuance later without rewriting business authorization. Never use the identity provider as the authoritative source for dynamic guardian-child or teacher-class permissions.
17.3 Authentication data model
Extend the existing users table rather than creating duplicate user records. Apply tenant-safe foreign keys where relevant. Authentication identities may span schools, while memberships and all resource permissions remain school-scoped. Never place raw refresh tokens, OTPs, passwords or MFA secrets in audit records.
17.4 OTP login and invitation flow
1. School administrator creates or imports a user and explicitly assigns the permitted school role and guardian/teacher relationships.
2. Issue a single-use invitation through an approved channel. Verify the invitation and phone ownership before activation; prevent unauthorized phone reassignment.
3. Client requests an OTP challenge. Return a generic response to avoid account enumeration. Apply per-identity, phone, IP and device throttles and provider abuse controls.
4. Generate a cryptographically secure code, store only a keyed hash, set a short expiry and enforce bounded attempts and resend cooldowns. Provider delivery is not proof of authentication.
5. Verify the code in a transaction, consume the challenge once, confirm account status and create a device session. Return a short-lived signed access JWT and opaque refresh credential.
6. Resolve active school membership and role context on the server. Require an explicit school/role selection where the user has multiple contexts.
7. On logout, revoke the session and clear sensitive local credentials/cache. Administrative suspension or guardian-link revocation must take effect independently of token expiry.
17.5 Token and session security
Use asymmetric JWT signing (for example RS256 or ES256) with managed private keys, a key identifier and a documented rotation procedure. Validate algorithm allowlist, signature, issuer, audience, expiry, not-before and token type. Reject unsigned tokens, unexpected algorithms and client-controlled signing keys. Never use a hard-coded or default production secret.
Access JWT claims should be minimal: subject, session ID, issuer, audience, issued/expiry times and token identifier. School and role may be contextual hints but are not authorization proof. Resolve current membership and resource permissions server-side. Use a 5–15 minute access-token lifetime as a proposed starting point, subject to threat review and pilot testing.
Generate refresh tokens using a cryptographically secure random source. Store only keyed hashes; rotate on every successful refresh using an atomic compare-and-swap or row lock. Detect reuse and revoke the token family, with an explicit policy for concurrent refresh requests. Enforce configurable idle and absolute expiry, device/session limits, account suspension and administrator-initiated revocation. A short-lived access token may remain valid until expiry unless a session-status check or revocation cache is used; use such checks for sensitive operations and define the acceptable revocation latency.
Store mobile refresh credentials in OS-backed secure storage, never AsyncStorage or logs. Keep access tokens in memory where practical. For the admin web application, prefer a same-origin backend-for-frontend session using Secure, HttpOnly, SameSite cookies with CSRF protection; do not persist bearer tokens in localStorage. Use TLS, strict CORS and appropriate security headers.
17.6 API contract additions
All endpoints require complete OpenAPI schemas, request validation, standardized error responses, audit events and explicit rate limits. OTP request responses must not reveal whether a phone number exists. Refresh and logout endpoints must not accept a user ID as authority to act on another user. Administrative actions require server-side permissions and step-up authentication where appropriate.
17.7 Authorization remains unchanged
Authentication only establishes identity. Every protected operation must resolve active membership, role permissions, tenant scope and resource-specific relationships. Teachers must be assigned to the relevant class/subject; guardians must have an active explicit link to the student; result access must be checked on every request and file-access grant. Do not embed entire student lists or teacher assignments in JWTs. Revocation of a guardian link must invalidate future access even when an existing access token has not expired.
17.8 MFA, recovery and abuse prevention
Require stronger authentication for school administrators and result-publishing approvers. The exact MFA mechanism (such as TOTP or a managed identity provider) requires a security decision; SMS OTP alone is not automatically sufficient for privileged access. Provide secure account recovery, phone-number change and lost-device procedures with identity verification and audit. Never let support staff bypass guardian-link approval or reset an account based solely on possession of a phone number.
Enforce rate limits at the gateway and application, OTP attempt limits, resend cooldowns, per-user/device/session controls, provider spending limits and anomaly monitoring. Use generic errors to limit enumeration. Store minimal abuse telemetry with defined retention. Protect against SIM-swap/social-engineering risk through step-up verification for sensitive account changes.
17.9 Testing and production acceptance
Add tests for expired/replayed OTPs, concurrent verification, refresh rotation races, token-family reuse, revoked sessions, disabled users, changed school roles, revoked guardian links, signing-key rotation, malformed JWTs, account enumeration, rate-limit bypass, phone reassignment and privileged recovery. Verify all tests across multiple API replicas and during rolling deployments. Perform an independent authentication/security review before pilot release.
Production readiness requires secure key management, backup/restore of identity and session data, monitored OTP delivery, session-revocation runbooks, security event alerts, documented recovery procedures and no default credentials. Measure authentication latency, OTP success/failure rates, refresh errors, session counts and abuse-related provider costs. Do not claim that removing Keycloak automatically makes the solution more secure or cheaper overall; include engineering and security maintenance in the cost assessment.
17.10 Future external identity provider migration
Keep stable internal user UUIDs and map external provider subjects to auth_identities. Introduce an OIDC adapter, migrate or re-enroll users through an approved verification process, and preserve existing school memberships and guardian-child links. Never assume password hashes, OTP sessions or refresh tokens can be transferred between providers. Plan token issuer transition, client updates, session invalidation, rollback and audit continuity. Consider Keycloak, managed OIDC or enterprise federation only when requirements justify the additional dependency.
ADR-002: Adopt NestJS-managed invitation/OTP authentication for the MVP, with secure rotating sessions and application-owned authorization. Defer Keycloak and other external identity providers. This decision reduces initial infrastructure complexity but requires explicit security ownership and independent validation. It does not alter the approved business scope, privacy model or modular-monolith scaling strategy.
